1. The Problem

Why does OKD need automated documentation?
  • The central docs team is withdrawing support for OKD documentation
  • OpenShift targets a 4-month release cadence (3 releases per year) — manual doc writing can't keep up
  • Existing OKD docs are outdated (still reference Fedora CoreOS, wrong operators)
  • Each release touches 50-200 user-facing changes across multiple repos that need documenting

The gap: Without automation, documenting each release requires significant manual effort from an already-stretched docs team. Code changes happen across multiple repositories, and keeping docs in sync takes days of manual work per release cycle.

2. The Idea

One simple formula drives the entire system:

Docs(4.x) = SKILL.md + Docs(4.x-1) + CodeDiff(4.x-1 → 4.x)

In plain English: Give the LLM a trained skill, last version's docs, and what changed in the code — get new version's docs.

What is a "Code Diff"?

Not a raw git diff. It's a structured, filtered summary of documentation-relevant code changes across multiple repositories:

  • Full file contents of key Go type files (shows struct definitions, field comments, defaults)
  • CRD schema sections with field hierarchy context
  • Filtered key changes (only lines matching doc-relevant patterns)
  • Commit messages (explain the intent behind changes)
  • New/deleted file lists (shows structural additions/removals)

3. The Heart: SKILL.md

A SKILL.md file is a detailed instruction manual for the LLM. It tells the AI exactly:

What to look for in diffs
  • New CLI commands or flags
  • Changed API types or CRD fields
  • New upgrade preconditions
  • Behavioral changes (drain, reboot)
  • Version number patterns
Rules to follow
  • Don't fabricate content
  • Don't bump admin-ack without evidence
  • Use test fixtures for CLI output
  • GA promotions = primary command switch
  • Leave unchanged files alone

5. How We Measure Quality

Deterministic Scoring (fast, automated)

Run with make score VERSION=4.17 SECTION=updating — takes seconds.

MetricWhat it measuresHow
File CoverageAre all expected files present?Count files in generated vs ground truth
Text SimilarityHow close is the content line-by-line?difflib.SequenceMatcher ratio (0-100%)
Section CoverageAre all section headings present?Extract == Heading patterns, check presence
Param CoverageAre all parameter names mentioned?Extract backtick-quoted terms, check presence

LLM-Based Evaluation (deeper, semantic)

Run in a separate agent window — takes 10-20 minutes per version.

MetricWhat it measuresHow
Semantic AccuracyAre the facts correct?LLM reads each file, classifies as correct/minor/major issue
CompletenessAre ALL code changes reflected?LLM reads diff, checks each change is documented
StructureAre AsciiDoc conventions followed?Check headers, IDs, includes, attributes
Command AccuracyAre CLI commands correct?Verify against actual source code

Why two levels? Deterministic scoring is great for catching surface problems (missing files, wrong version numbers). But it can't tell if the meaning is right. An LLM judge can read the code and verify that documentation accurately describes what the code does.

LLM Evaluation (4.17 — two rounds)

We discovered that giving the LLM richer code context dramatically improves quality. "Enhanced diffs" include full Go type file contents, CRD schema sections, and wider diff hunks — instead of just the changed lines.

MetricBefore (basic diff)After (enhanced diff)Change
Semantic Accuracy91.2%92.7%+1.5
Completeness46.4%80.8%+34.4
Parameter Accuracy82.3%94.7%+12.4

What changed? A "basic diff" shows only the changed lines (like a typical git diff). An "enhanced diff" includes the full contents of key files — Go struct definitions with field comments, CRD schemas with field hierarchies, and CLI source code. This gives the LLM enough context to correctly name parameters, describe defaults, and write accurate procedure steps.

Note: LLM evaluation is expensive (10-20 min per version). We ran it in depth for 4.17 to validate the approach, then used deterministic scoring for the remaining training iterations.

Why are LLM scores lower than deterministic? Deterministic scoring measures surface similarity — most files are copied unchanged and score 100%. LLM evaluation focuses on the ~10-15 files that should have changed. Those files carry the hardest changes: product decisions, non-monitored repo changes, and editorial restructuring. The LLM judge penalizes every missed change, even if it's invisible in code diffs.

Critical Discovery: No Subagents

Subagents break doc generation. When the LLM splits work into parallel tasks ("version sweep" + "MCO docs" + "status update"), each subagent loses context of the full rule set and other changes. Result: contradictory edits, fabricated content, rule violations.

ApproachStructure ScoreConsistency
Single agent95-100%No contradictions
Subagents45%Conflicting edits

Why Two Sections? Installing vs Updating

We trained the system on two different documentation sections to test whether the approach generalizes. Each section has different characteristics:

Installing — Large, code-heavy
  • 189 assemblies across multiple platforms (AWS, GCP, Azure, vSphere...)
  • Heavy on install-config parameters, Go structs, CRD schemas
  • Most changes are directly traceable to code commits
  • Bigger section = more files to process, but more code-derivable content
Updating — Smaller, more procedural
  • ~30 assemblies focused on upgrade workflows
  • Heavy on CLI commands (oc adm upgrade), CVO behavior, MCO drain logic
  • More changes driven by product decisions (deprecations, GA promotions)
  • Smaller section = faster iterations, but more "invisible" changes

Key finding: The approach works across both section types. Deterministic scores are comparable (~95-97% on stable releases). The LLM evaluation gap between sections reflects the nature of the content: installing docs are heavily code-derived (Go structs, CRDs), so the LLM covers most changes. Updating docs depend more on product decisions (deprecations, GA promotions, editorial restructuring) that are invisible in code diffs, making the LLM evaluation stricter.

7. Where We Did Well

Installing Section — Wins
  • 93% average text similarity across 189 assemblies
  • Completeness jumped from 46% → 81% with enhanced diffs
  • Parameter accuracy 94.7% — Go comments correctly mapped to docs
  • New platform fields (nutanix, vsphere) correctly documented from struct definitions
  • install-config parameters extracted accurately from CRD schemas
  • Handles 7 repos simultaneously without losing coherence
Updating Section — Wins
  • 97% average text similarity (excl major transitions)
  • 98.8% peak accuracy (4.21) — near-perfect generation
  • CLI commands always verified against source code
  • Admin-ack logic correctly handles presence/absence
  • Version sweeps (kubelet, channels, repos) reliably applied
  • Perfect AsciiDoc structure — zero agent-introduced convention violations

Agent Ahead of Ground Truth (Both Sections)

In several cases, the AI documented real code changes that human-written docs hadn't caught up to:

Installing
  • New install-config fields documented before human writers added them
  • Platform constraint updates from validation.go reflected faster
  • CRD schema changes captured same-day from source
Updating
  • oc adm upgrade status new operator-count format

Potential Improvements: Extending the Inputs

The core approach (SKILL.md + iterative training) stays the same. What changes is giving the LLM more context beyond just code diffs:

Adding JIRA/Epic Context to Close the Gap

Every release has a set of tracked epics in JIRA. By feeding the LLM the list of epics targeted for a release, we can address the categories that code diffs miss:

Gap CategoryHow JIRA Helps
Product deprecationsEpics explicitly track deprecation decisions (e.g., "Remove RHV support", "Drop RHEL compute node docs")
Non-monitored reposEpics link to PRs across ALL repos, not just the 5-7 we watch. The LLM can discover which repos changed.
New content creationEnhancement epics describe new features that need documentation from scratch, with acceptance criteria the LLM can use.
Content relocationDocs-team epics may describe IA restructuring plans the LLM can follow.

Impact: Adding JIRA context could close 10-15% of the current gap — bringing automated coverage from ~75-80% up to ~90% — without changing the core formula: Docs(4.x) = Docs(4.x-1) + CodeDiff + JiraContext

Other Potential Extensions
More source repos

Adding repos as we discover gaps. We went from 3 → 7 for installing and 3 → 5 for updating during training. This can continue as needed.

Release notes as input

PRs with release-note blocks contain human-written summaries of user-facing changes. These can supplement code diffs.

9. Key Lessons

Architecture Lessons (Both Sections)
  1. Single agent is mandatory — subagents destroy consistency (discovered in updating, applies universally)
  2. Enhanced diffs >> basic diffs — full Go type files give +34% completeness (installing), full CVO/oc source gives accurate CLI docs (updating)
  3. Multiple repos are essential — installing needs 7, updating needs 5. No single repo has all changes.
  4. Iterative training works — installing: 12→23 rules. Updating: 12→28 rules. Each pass fixes real failures.
  5. Section-dynamic architecture — project reorganized to support any section (installing, updating, future) with shared tooling
Content Lessons (Both Sections)
  1. Don't fabricate — installing: don't invent platform fields. Updating: don't invent admin-ack gates.
  2. Code comments ARE documentation — Go struct field comments map directly to parameter descriptions (installing). CLI help text maps to procedure steps (updating).
  3. Version sweeps need evidence — installing: don't bump callout lists blindly. Updating: don't bump Kubernetes API removals without checking.
  4. GA promotions = workflow change — when a feature gate is removed, the command becomes THE primary approach (updating). When a TP platform becomes GA, it gets full procedure docs (installing).
  5. "Don't do X" needs "do Y instead" — prohibition rules without alternatives cause confusion in both sections.

10. Production Readiness (4.23+)

When there's no ground truth (future versions), the categories shift:

What the AI handles — Installing
  • New install-config fields from Go structs/CRD schemas
  • Platform constraint changes (validation rules)
  • New platform support stubs (from installer code)
  • Permission/IAM policy changes per platform
  • Firewall/port requirement updates
  • Version string sweeps across 189 files
  • Correct AsciiDoc structure and includes

= ~80% of install doc changes automated

What the AI handles — Updating
  • New CLI commands and flags (oc adm upgrade *)
  • Changed CLI output formats (from test fixtures)
  • New CVO preconditions and upgrade gates
  • MCO behavioral changes (drain, reboot)
  • Admin-ack gate detection (API removals)
  • Version sweeps (channels, kubelet, repos)
  • Feature gate → GA promotion workflow changes

= ~75% of update doc changes automated

What humans still do (both sections)
  • Content reorganization decisions
  • New platform/feature documentation from scratch
  • Cross-section coordination (xrefs, includes)
  • Product deprecation and removal notices
  • Editorial quality review
  • Final approval before publishing

= 20-25% requires human editorial layer

Bottom line: The pipeline generates a high-quality first draft that is 93-99% accurate on code-derivable changes. The docs team reviews, adds product context, and approves. Time savings: days of manual writing → focused review and editorial polish. This applies across any documentation section we train a skill for.

Scaling to More Sections

The same approach applies to any documentation section. To add a new section:

  1. Identify relevant source repositories for that section
  2. Create a SKILL.md with section-specific rules (start with ~12 generic rules)
  3. Run the training loop against versions 4.16-4.22 to grow the rule set
  4. The section is now ready for production generation
