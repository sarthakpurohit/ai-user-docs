1. Problem & Goals

Why This Exists

The central docs team is withdrawing OKD documentation support. After their departure, there will be no human writers maintaining installation documentation for OKD releases.

We need an AI system that can automatically generate accurate user-facing docs for each new version (4.23+), using only source code changes as input.

No human docs writers for future versions ~950 AsciiDoc files per version Changes span 7+ repositories Must match existing doc conventions exactly
POC Scope

Focus on the installation section of documentation only. If successful, expand to networking, storage, operators, etc.

Use OpenShift 4.16 → 4.22 as training data (ground truth exists). Deploy on 4.23 where no ground truth will exist.

2. Methodology — What We Did

Step-by-Step Process
  1. Extracted installation docs for OCP/OKD versions 4.16 through 4.22 from openshift/openshift-docs (branch enterprise-4.XX)
  2. Cloned 7 source repositories that contribute to installation features
  3. Generated structured multi-repo diffs between consecutive release branches (e.g., release-4.17 → release-4.18)
  4. Created SKILL.md — an instruction file teaching the LLM how to transform code changes into doc updates
  5. For each version pair: Generated docs using only previous docs + code diff + skill, then compared against actual docs
  6. Updated SKILL.md with lessons learned from each evaluation, creating versioned snapshots

Inputs

  • Diff: Structured summary from 7 repos — new/deleted/modified files, key code changes, commit messages
  • SKILL.md: 5-phase process: Analyze → Generate → Format → Validate → Summarize
Outputs
  • Generated docs: Updated AsciiDoc files for version 4.x
  • Evaluation report: Per-file metrics vs ground truth
  • Updated SKILL.md: Refined with new lessons

Core insight: ~95-98% of documentation is unchanged between minor versions. We exploit this by starting from the previous version and only modifying what the code diff requires.

3b. What "Code Diff" Actually Means

Important clarification: "Code diff" in our project does NOT mean the raw line-by-line git diff output. It's a structured, filtered, summarized extract of only documentation-relevant changes.

Why not use raw git diff?

A raw git diff between release-4.17 and release-4.18 across 7 repos produces 50,000+ lines of output — far too much noise for an LLM. Most of it is implementation details, test fixtures, and vendor dependencies irrelevant to user-facing documentation.

Instead, we extract a ~200KB structured summary (~4000 lines) containing only what matters for doc generation.

The 5 Components of Our "Code Diff"

① Overview Statistics
- New files: 17
- Deleted files: 2
- Modified files: 97
- Total commits: 40

Tells the LLM the scale of change. Many new files = likely new features needing new doc modules.

② Key Code Changes Filtered — Not all lines

This is the critical part. We run git diff -U2 but then filter to only keep lines matching this regex:

(type |struct|interface|func |//|json:|yaml:|description|spec\.|status\.)

This means we only keep:

PatternWhat It CapturesWhy It's Doc-Relevant
type / structGo type and struct definitionsThese define install-config fields that become doc parameters
interfaceGo interface changesNew capabilities or API contracts
func Function signaturesNew CLI commands, validators, install steps
//Go commentsOften contain field descriptions that become doc text
json: / yaml:Struct field tagsThe actual parameter names users will configure
descriptionCRD schema descriptionsDescriptions written in CRDs often become doc text verbatim
spec. / status.API spec/status referencesMaps directly to documented API fields

We skip: implementation details, variable assignments, error handling, test assertions, import statements, vendor code.

Additional limits: Max 40 hunks per file, max 30 files per repo.

5. Evaluation Metrics — How They're Measured

The evaluation script (evaluate-generated-docs.py) compares every generated file against its actual counterpart. Four primary metrics are reported:

File Coverage

File Coverage = |Generated ∩ Actual| / |Actual|

What: Of all documentation files that should exist, what percentage did we produce?

How: Files are matched by basename (filename). If actual has 969 files and 880 match our generated set → 880/969 = 90.8%

Catches: Entirely missing docs — new modules, new assembly pages, new platform guides that weren't created.

Penalty: Missing files are scored as 0% on ALL other metrics — they drag down every average significantly.

Text Similarity

Text Similarity = difflib.SequenceMatcher(generated_lines, actual_lines).ratio()

What: Line-by-line content similarity between generated and actual file.

Library: Python's built-in difflib.SequenceMatcher (part of the standard library, no external dependencies).

How SequenceMatcher Works (Gestalt Pattern Matching)

The algorithm finds the longest common subsequences between two sequences (in our case, arrays of lines). It's based on the Ratcliff/Obershelp algorithm:

  1. Find the longest contiguous matching block between the two sequences
  2. Recursively find the longest matches in the portions to the left and right of that block
  3. Continue until no more matching blocks of a minimum size exist

The .ratio() method returns:

ratio = 2.0 * M / T

Where M = number of matching elements (lines) across all common subsequences, and T = total number of elements in both sequences combined.

Concrete Example

# Generated file (5 lines):
= Installing on AWS
You can install on AWS using IPI.
== Prerequisites
* An AWS account
* The `openshift-install` binary

# Actual file (6 lines):
= Installing on AWS
You can install on AWS using IPI.
== Prerequisites
* An AWS account
* IAM permissions (see table below) ← new in actual
* The `openshift-install` binary

# Result: M=5 matching lines, T=5+6=11 total
ratio = 2*5/11 = 0.909 = 90.9%

Pre-processing Before Comparison

Before computing similarity, both files are normalized:

  • AsciiDoc comment lines (starting with //) are stripped — except module metadata like // Module included in...
  • Whitespace is preserved (indentation matters in AsciiDoc)
  • Files are split into arrays of lines — comparison is line-by-line, not character-by-character

Catches: Wrong wording, missing paragraphs, incorrect version numbers, outdated URLs, missing code examples.

Interpretation guide: 95%+ = minor differences (URLs, IDs). 80-95% = some sections changed. 50-80% = significant rewrite. Below 50% = file was restructured or replaced.

Section Coverage

Section Coverage = |sections_generated ∩ sections_actual| / |sections_actual|

What: Of the AsciiDoc section headers (= Title, == Section) in the actual doc, what percentage exist in our generated version?

How: Regex extracts all lines starting with =+\s+. Compares by exact header text. If actual has 6 sections and generated has 5 matching → 5/6 = 83%.

Catches: Missing entire topics, missing procedure steps, missing reference sections. Can reveal structural problems even when text similarity is high.

Parameter Coverage

Param Coverage = |params_generated ∩ params_actual| / |params_actual|

What: Of configuration parameter names in the actual doc, what percentage appear in our generated version?

How: Regex extracts backtick-quoted identifiers matching `word.with.dots` or `lowercaseWord` patterns. These capture install-config fields, API fields, CLI flags.

Catches: Missing configuration options. If 4.18 adds `platform.nutanix.failureDomains[].subnets` and we don't document it, this metric drops.

Why critical: Installation docs are parameter-heavy. Missing a parameter = users don't know the option exists.

Aggregate Scoring Method

Final reported percentages are averages across all files INCLUDING missing files scored as 0%. This means:

  • A version with 89 missing files out of 969 will have significantly lower averages even if matched files are 99% similar
  • This design choice penalizes the generator for not creating new documentation — which is the hardest problem
  • It simulates real-world impact: missing docs = users can't find information

8. Key Findings & Interpretations

Finding 1: ~95% accuracy is achievable with code-diffs alone

Across 5 of 6 iterations, we consistently achieved 94-97% text similarity. The version bump + targeted feature changes strategy works.

The remaining ~5% gap consists of:

  • New documentation modules (25-39 files/version) not predictable from code
  • Firewall allowlist URLs that change outside monitored repos
  • AMI IDs, region data from release engineering
  • Editorial improvements by the docs team
Finding 2: Documentation restructuring is the #1 accuracy killer

The 4.19→4.20 iteration scored 83.2% — a 13% drop from adjacent versions. Root cause: editorial file reorganization.

Restructuring PatternImpact
SNO docs split into 6 separate modules6 new files not generated, parent files restructured
Azure VNet docs split into 3 modulesOriginal drops to 7.6% similarity
FIPS docs split into 2 modulesParent restructured + 2 missing files
Overview page completely rewritten4.6% similarity
vSphere config examples major rewrite22.4% similarity

These are editorial decisions — not driven by code changes. They happen every 2-3 versions. Requires docs team planning signals to predict.

Finding 3: New product integrations are invisible to our analysis

Each version adds docs for features whose changes don't appear in our 7 repos:

4.18C3 (Compute Cloud@Customer) from Oracle integration~10
4.19BMaaS (Bare Metal as a Service) from infra team~6

Finding 4: What works well vs. what doesn't

Works Well (95%+)

  • Version reference bumps (release-4.x URLs)
  • New install-config parameters from CRD diffs
  • Tested instance type additions
  • Feature gate promotions (TechPreview → GA)
  • Platform constraint limit updates
  • Capability set version additions
  • Include directive preservation

Doesn't Work (< 80%)

  • File restructuring / splits / renames
  • New product integrations (C3, PCA, PowerVC)
  • Firewall URL rewrites (3.7% every time)
  • Editorial rewrites for clarity
  • Cross-product documentation
  • IaC template migrations (DM → Infra Mgr)
  • AMI/image ID updates per region

10. Next Steps

  1. Deploy for 4.23 — Use the trained SKILL.md to generate 4.23 docs from 4.22 + diffs. This is the real test: no ground truth.
  2. Integrate supplementary signals — Connect to docs team Jira for restructuring plans and enhancement proposals for new features.
  3. Expand to other sections — Apply the methodology to networking, storage, and operator documentation.
  4. Automate with GitHub Actions — Trigger on release branch creation → generate diffs → apply skill → create draft PR.
  5. Confidence-based routing — Auto-approve high-confidence updates (version bumps); flag low-confidence items (new modules, restructured files) for human review.
  6. Run eval harness — Use opendatahub-io/agent-eval-harness for formal scoring with deterministic + LLM judges on final outputs.
