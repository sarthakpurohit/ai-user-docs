1. The Problem with difflib

Our previous evaluation used difflib.SequenceMatcher

It compares text line-by-line and reports a similarity ratio. For our first 6 iterations, it showed:

~95%
Text Similarity
~95%
Section Coverage
~95%
Parameter Coverage

This looked great. But it was misleading.

The hidden truth: When we ran an LLM-based evaluation that actually READ the code diff and checked whether each change was documented, completeness was only 46.4% — the skill was missing HALF the changes while still scoring 95% on text similarity.

2. Our Approach: 3-Way LLM Evaluation

Baseline 4.16 → Generated 4.17 vs Ground Truth 4.17
The LLM judge sees ALL THREE versions

For every file, the judge determines:

ClassificationMeaningWho's at fault?
UNCHANGED_CORRECTSame in all three (baseline = generated = ground truth)Nobody — file didn't need changing
CORRECTGenerated matches ground truth semanticallyNobody — agent did it right
MINOR_ISSUESSmall inaccuracies (wrong optional/required, imprecise wording)Agent — minor fault
MAJOR_ISSUESWrong types, wrong defaults, fabricated content, missing critical infoAgent — serious fault

Four evaluation dimensions

Semantic Accuracy

LLM reads every common file. Classifies each as correct/minor/major. Files wrong in both 4.16 and generated are NOT penalized.

Completeness

LLM reads the full code diff. For each user-facing change, checks if it appears in generated output. Scored as COVERED or MISSED.

Structure Compliance

Checks AsciiDoc conventions: module headers, IDs, procedure format, attribute usage. Separates inherited-from-4.16 issues from agent-introduced ones.

Parameter Accuracy (Grounded)

For every new/changed parameter, reads the actual Go source code and verifies: name matches json tag, description matches comment, type correct, constraints correct.

6. Where AI Beats Human Docs

The evaluator explicitly noted: Generated docs are MORE accurate than the human-written 4.17 ground truth in several areas.

Fields documented correctly by AI but missed by human docs team
Field/FeatureAI GeneratedHuman Ground Truth
baselineCapabilitySet: v4.17✓ Documented with correct enum✗ Never added

GCP hyperdisk-balanced + AI zone filtering✓ Both documented~ Incomplete
AWS amiID platform deprecation✓ Marked deprecated with replacement✗ Still documented as current

Why this happens: Our approach uses Go source as ground truth. If the struct says // deprecated. Use X instead. — we document it. Human docs teams sometimes miss these because they rely on Jira tickets and release notes, not direct code inspection.

7. The Remaining 9% Gap

Fixable (~4%)
  • Validation-only constraint changes (no new field name)
  • Assembly ID format (_{context})
  • Sample device paths matching Go comments
  • Deeper BMO diff scanning
Not fixable by code diff (~5%)
  • Directory reorganizations (Azure IPI/UPI split)
  • Module renames (IBM Cloud classic)
  • Content merges/splits (editorial decisions)
  • Features from unmonitored repos
The "Unpredictable 5%" — Editorial Decisions

These changes exist in ground truth but have NO signal in any code repository:

  • Moving Azure docs from installing_azure/ to installing_azure/ipi/ + installing_azure/upi/
  • Renaming installing_ibm_cloud_public/ to installing_ibm_cloud_classic/
  • Removing disconnected_install/ from the installing book entirely
  • Splitting one large module into multiple focused modules

These require either docs-team planning documents, topic-map diffs, or human editorial review.

9. Conclusions

What Works
  1. Enhanced diffs are the biggest lever. Full Go files → +34% completeness.
  2. LLM eval finds what difflib can't. String matching said 95%, reality was 46% complete.
  3. Iterative refinement works. Each eval → specific rules → measurable improvement.
  4. Code-first beats human-first. AI catches fields humans miss because it reads the struct directly.
  5. 3-way eval is fair. Inherited issues don't penalize; only agent-caused errors count.
Limitations
  1. ~5% ceiling from editorial decisions. Not solvable by code diffs alone.
  2. Each LLM eval costs ~$5-10. Can't run on every commit.
  3. Non-deterministic. Same eval run twice may score ±2%.
  4. Unmonitored repos. BMO, CNO features come from repos we don't fully scan.
  5. Procedures need rewriting, not just param rows. Hardest to get right automatically.

Bottom line: With enhanced code diffs + iteratively-refined SKILL.md + LLM evaluation, we achieve 91% overall quality on a code-diff-only approach. The remaining 9% requires human editorial input or additional signal sources.
